# 多账号并发抢购：方案与实测数据

**结论先行：不需要指纹浏览器。** 一个 Chromium 进程 + N 个独立 context 就够，
120 个账号只吃 2.5 GB 内存。本机实测。

---

## 一、你的顾虑与技术真相

> "一个普通浏览器只能登录一个账号，多个账号就需要很多浏览器"

**前半句对，后半句不对。**

普通浏览器（你手动开的那种）确实一个 profile 只能登一个账号 —— 因为所有标签页共享同一份 Cookie。

但 Playwright 提供的 `browser.newContext()` 是**另一个层级的东西**：
一个 Chromium 进程里可以开 N 个 context，每个 context 有**完全独立**的
Cookie / localStorage / sessionStorage / cache，相当于 N 个互不干扰的浏览器。

**实测证据**（本机，`grab-probe/output/multi-account.json`）：

```
ctxA 的 cookie:        sid=ACCOUNT_A
ctxB 的 cookie:        <空>            ← 看不到 A 的
ctxA 的 localStorage:  ACCOUNT_A
ctxB 的 localStorage:  null           ← 看不到 A 的
判定: ISOLATED —— context 间完全隔离
```

顺带验证了反面：**同一个 context 内的多个 page 共享 cookie jar**
（page1 = `sid=ONLY_ONE`，page2 也是 `sid=ONLY_ONE`）。
所以"单 context 开多个标签页装多个账号"是行不通的 —— context 隔离正是它不可替代的原因。

---

## 二、容量实测：能同时跑多少个账号

本机 AMD Ryzen 5 5600（6 核 12 线程）+ 16 GB 内存，headless：

| 账号数(context) | 内存消耗 | 边际/个 | Chromium 进程数 | 事件循环延迟 |
|---|---|---|---|---|
| 10 | 218 MB | 21.8 MB | 13 | 12 ms |
| 30 | 507 MB | 21.1 MB | 27 | 11 ms |
| 54 | 1166 MB | 21.6 MB | 57 | 14 ms |
| 81 | 1715 MB | 21.2 MB | 84 | 11 ms |
| 120 | 2562 MB | 21.4 MB | 123 | 11 ms |

**每个账号约 21 MB，线性增长，没有拐点。** 120 个账号占 2.5 GB，
6 核还能维持 11 ms 的事件循环延迟（说明没被拖垮）。

每个 context 一个独立 renderer 进程，共享同一个 browser 进程 —— 这是省资源的关键。

渲染能力：50 个 context 同时跑动画，每页仍是 60 fps，整机约 2 个核忙碌。

## 三、★ 最大的坑：同一个 profile 目录不能双开

**这个坑不会报错，而是以更难查的方式表现出来。**

实测：两个进程同时打开**同一个** `userDataDir`：

```
进程 A: 正常，看到自己的 cookie ACCT_A
进程 B: 正常，看到自己的 cookie ACCT_B     ← 两者内存态各自独立，看似没问题
```

但底层磁盘 profile 被两个 Chromium 实例并发读写：

```
步骤耗时对比：
  addCookies:  单开 4ms  →  双开 1458ms    （慢 364 倍）
  close():     单开 1277ms →  双开 > 10 秒挂死
```

**Windows 上 Chromium 不对 `userDataDir` 做硬锁**，双开不会立刻失败，
而是随机出现 IO 竞争、句柄争用、关闭挂死。比直接报错危险得多 ——
因为它可能在你抢购那一刻才发作。

→ **铁律：一个账号一个独立 profile 目录，且同一时刻只能有一个进程打开它。**

## 四、推荐架构

```
进程模型：
  单 Node 主进程 + 单个 Chromium 实例 + N 个 browser.newContext()

为什么不用多进程：
  单个 launchPersistentContext = 一个独立 Chromium 实例（独立 browser 进程），
  进程数和内存都翻倍。120 个账号用单进程 + 120 context 就够。

目录布局：
  profiles/
    account-a/     ← 账号 A 的 userDataDir（只用于「登录态维护」）
    account-b/
    profiles/state/
      account-a.json   ← 导出的 storageState（cookie + localStorage）
      account-b.json

两阶段工作流：
  【平时】维护登录态
    每账号一个 persistent context，用户手动登录一次，保存 profile。
    这一步一次性完成，之后不需要再登录（cookie 有效期通常够长）。

  【开抢时】批量建 context ★ 关键
    不再用 persistent context（会有目录锁问题），
    改为把每个账号的 profile 导出成 storageState(JSON)，
    用 browser.newContext({ storageState }) 批量创建。
    已实测可完整还原 cookie + localStorage。
```

**实测：5 个账号并行用各自独立目录，全部成功**（1.85 秒内全部就绪）。

## 五、时刻对齐：怎么让 N 个账号在同一刻行动

### 时钟精度实测

- `Date.now()` 步进 0~1 ms，分辨率够用
- `setTimeout` 精度 p50 = 6 ms，max = 16 ms（**不够准**）
- `setInterval(1ms)` 精度 p50 = 2 ms（好一些）
- **页面内忙等** `while (Date.now() < T0) {}` 精度最高

### 跨进程对齐实测

8 个进程以同一绝对时刻（epoch ms）忙等对齐：

```
driftPerProcMs: [0,0,0,0,0,0,0,0]     ← 全部零偏差
wakeTimeSpreadMs: 0
```

**结论：本机所有进程能精确对齐到同一毫秒。**

### 实际到达时间（最要紧的数字）

N 个 context 同时"开火"（各自发一个请求），服务端看到的到达时刻离散度：

| 账号数 | 客户端唤醒离散 | 服务端到达离散 |
|---|---|---|
| 1 | 0 ms | 0 ms |
| 10 | 0 ms | **4 ms** |
| 30 | 6 ms | **17 ms** |
| 50 | 13 ms | **32 ms** |

**50 个账号在 32 毫秒内全部到达。** 对抢购来说完全够用（人手点做不到这个同步度）。

### 做法

```
1. 定一个绝对目标时刻 T0（epoch ms），所有账号共用
2. 每个 context 的页面内执行：
     while (Date.now() < T0) { /* 忙等 */ }
     立即触发动作
3. 关键路径不要跨 CDP 往返等待
   （Node → CDP → renderer 的往返本身就有毫秒级抖动，
     所以忙等要放在页面内，不要放在 Node 侧）
```

## 六、CDP 并发开销

| context 数 | 吞吐 | 往返 p95 |
|---|---|---|
| 1 | 380 req/s | 1.1 ms |
| 10 | 1225 req/s | 5.2 ms |
| 30 | 1200 req/s | 18.1 ms |
| 50 | 1158 req/s | 37.4 ms |

吞吐在 10 context 后饱和（约 1200 req/s），继续加只是持平。
**抢购场景每个账号只发少量请求，完全够用** —— 不要用它做高频轮询。

## 七、为什么不推荐指纹浏览器

| | Playwright 多 context | 指纹浏览器（Multilogin/AdsPower 等） |
|---|---|---|
| 登录态隔离 | 天然支持，实测有效 | 支持 |
| 成本 | 0（已有） | 通常按月收费 |
| 容量 | 120 个占 2.5 GB | 取决于机器，但要开多个实例 |
| 自动化 | 原生 API，好写 | 需要对接其 API，多一层 |
| 适用场景 | **本机多账号** | **跨设备/跨环境的一致指纹伪装** |

指纹浏览器解决的核心问题是"同一账号从不同设备登录时保持指纹一致"，
以及"平台检测浏览器指纹时伪装成不同设备"。

你的场景是**本机同时登录多个自己的账号**，需要的是**登录态隔离**，
不是指纹伪装 —— 而登录态隔离用 context 就够了。

**唯一需要指纹能力的情况**：平台明确按浏览器指纹识别并限制多账号。
这属于风控对抗，不在本方案范围内（本方案的边界是：正常登录、正常浏览、正常点击）。
