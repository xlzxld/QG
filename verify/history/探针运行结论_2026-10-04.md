## 1. 结论先行

**核心问题已由华为商城（vmall）得到回答。**

| 问题 | 状态 |
|---|---|
| 共享会话能否稳定读取多个商品页的库存状态 | **能** —— 华为商城 3 个目标 × 2 轮全部可判定且稳定，零拦截（详见第 3 节） |
| 哪些平台可退化为纯 HTTP 探测 | **华为商城不可退化为纯 HTTP**，且获得了机制层面的解释（详见第 4 节） |
| 探针自身的分类器是否可信 | 首轮存在误判，**已定位并修复**，经三轮复跑验证（第 5 节） |
| 单页读取耗时量级 | 中位 2.9 秒/页（headless 完整 Chromium，串行）；4 个平台合计区间 0.9～4.6 秒 |
| 共享会话一轮全量检查耗时 | 3 个目标 ≈ 8.7 秒；按此推算 100 个目标 ≈ 5 分钟 |
| 商品 URL 是否会静默失效 | **会** —— 苹果目标指向已下架机型，被重定向到导购页（第 2.2 节） |

**对审查报告第 2.3 节的影响**：该节把 Monitor 层"纯 HTTP 轮询"降级为"共享会话读渲染结果"的处理**得到实测支持**，且现在有了机制层面的证据，不再只是线索。

**仍未回答**：京东需登录态后的表现（第 7 节给出复跑指引）；天猫、NVIDIA 未测。

### 2.1 苹果那条 `blocked` 是分类器误判，不是风控

证据文件显示 `FINAL: https://www.apple.com.cn/shop/buy-iphone`，页面渲染完全正常（导航与正文均读到），却因正文中出现 `限制` 二字命中了我写的 `IP.*(限制|封禁)` 正则。

同一页面还有第二个误判：命中的 `preorder("预约")` 来自 Apple 正文「可**预约**到店升级换购」——那是零售店服务预约，与商品预售无关。

**这不是平台行为，是探针缺陷。** 已修复（见第 5 节）。

### 2.2 苹果目标 URL 本身已失效

`https://www.apple.com.cn/shop/buy-iphone/iphone-17-pro` 被重定向到机型选购页 `/shop/buy-iphone`。

原因经外部核验确认：**iPhone 17 Pro 系列已于 2026-09-10 从苹果中国官网下架**，官网仅售基础机型及更早型号（[明报 2026-09-10](https://news.mingpao.com/ins/%e7%86%b1%e9%bb%9e/article/20260910/s00024/1789026302075/iphone17-pro%e7%b3%bb%e5%88%97%e9%a6%99%e6%b8%af%e5%85%a7%e5%9c%b0%e8%98%8b%e6%9e%9c%e5%ae%98%e7%b6%b2%e4%b8%8b%e6%9e%b6-%e5%83%85%e5%94%ae%e5%9f%ba%e7%a4%8e%e5%8f%8a%e6%9b%b4%e6%97%a9%e5%9e%8b%e8%99%9f-%e5%ae%a2%e6%9c%8d%ef%bc%9a%e8%bf%ad%e4%bb%a3%e5%8d%87%e7%ba%a7%e4%b8%80%e8%b2%ab%e5%81%9a%e6%b3%95#top)）。因此重定向是该站的**正常行为**，不是反自动化措施。

**这恰好印证了审查报告第 10 节的未验证项之一**：手工编写商品 URL 不可靠。商品会下架、URL 格式会变，目标清单必须能自动校验。

### 2.3 京东需要登录态（这是有效的架构约束）

两个京东目标都被重定向到 `passport.jd.com/new/login.aspx`，页面渲染出登录表单，分类为 `gated`（登录墙），标签 `login_wall`，判定正确。

**这条结论本身有价值**：不带登录态的会话读不到京东的商品与库存状态。因此京东类平台的监控架构中，**会话必须先维持登录态**，profile 的持久化与租约管理是必要条件而非优化项 —— 这与审查报告第 8.1 节的"Profile 租约 + 归档存储"设计互为印证。

### 3.1 共享会话判定成功（探针的核心问题）

- **3 个目标 × 2 轮，6/6 全部可判定**，且两轮结论完全一致（`in_stock` / `preorder`）
- **拦截计数为 0** —— 6 次连续导航未触发任何验证或限流
- 3 个不同 URL 由**同一个持久会话**在 8.7 秒内完成一轮全量检查

判定内容经人工抽查确认无误：

| 目标 | 判定 | 页面实际内容 |
|---|---|---|
| Mate 80 | `in_stock` | ¥5499、12GB+256GB 云杉绿、实时「加入购物车 / 立即购买」按钮、「送至 广东 深圳 龙岗区」「预计48小时内发货」 |
| 麦芒 9（旧款 URL） | `preorder` | 落地为「华为麦芒 9 5G」，页面标题含「【订金商品】」 |

### 3.2 桌面 URL 与移动 URL 都被归一化

两个 Mate 80 目标（`www.vmall.com/product/10086133363559.html` 与 `m.vmall.com/product/comdetail/index.html?prdId=...`）**都落到同一个最终地址**：

```
https://item.vmall.com/product/comdetail/index.html?prdId=10086133363559&sbomCode=
```

**架构含义**：华为商城把长短链统一收敛到一个商品详情页模板。这意味着适配器只需针对**一个页面模板**编写选择器与判定规则，不必为桌面/移动/短链分别维护 —— 对阶段 4 的 `Brand Official Web Adapter` 是明显利好。

### 3.3 旧款 URL 会跳到另一个商品（目标漂移）

`https://www.vmall.com/product/10086741488253.html` 请求的是「麦芒 9 5G」，落地标题也是「华为麦芒 9 5G」—— 本例中未发生漂移。但**苹果目标的重定向先例已证明目标会静默改变**（见 2.2），而探针当时把它误判为风控。

因此第 4.7 节（审查报告）的结论在此再次得到支持：**商品任务必须假设"配置一次长期有效"是错的。**

## 4. 机制层面的发现：库存状态由客户端脚本注入（决定性）

针对"Mate 80 有 833 KB 初始 HTML 却读不出库存，而旧款 433 KB 就能读出"这一反常现象，做了一次对照核查：同一 URL 分别取**禁用 JS**（≈纯 HTTP 客户端）与**启用 JS**（浏览器渲染）两种情况下**用户可见文本**，只读 `body.innerText`，不拦截任何响应体。

| 页面 | 禁用 JS | 启用 JS 渲染后 | 库存信号 |
|---|---|---|---|
| Mate 80 | HTTP 200，DOM 833,052 字符，**可见文本仅 339 字** | DOM 917,481 字符，**可见文本 8,475 字** | 仅渲染后出现「加入购物车」「立即购买」 |
| 麦芒 9（旧） | HTTP 200，DOM 433,198 字符，**可见文本仅 383 字** | DOM 688,443 字符，**可见文本 6,036 字** | 两者均含「订金」 |

### 4.1 结论一：初始 HTML 里没有可用信息

禁用 JS 时页面只渲染出 **339 / 383 字**，而 DOM 高达 83 万 / 43 万字符 —— 即 **99.9% 以上的内容是脚本与数据块，而非可见内容**。商品标题、价格、规格、库存状态全部由客户端脚本在渲染后填入。

**这是对"纯 HTTP 监控"否定的机制层面证据**：即使取到 HTTP 200 与完整的 833 KB 响应体，也拿不到任何可判定信息。

### 4.2 结论二：旧款那条"纯 HTTP 可判定"是假阳性，需降级

`huawei-p40-old` 在纯 HTTP 视角下被判为 `preorder`，看似"可省掉浏览器资源"。但对照核查显示该页面禁用 JS 时**可见文本仅 383 字**，其中出现的「订金」很可能来自 SEO 文本或内嵌数据块，而非用户真实可见的交互状态。

**处理：该 `HTTP可判定` 计数不可作为"可退化为纯 HTTP"的依据。** 探针的 HTTP 视角判定应增加一条约束：**可见文本量过低（例如 < 1500 字）时不得据此判定库存状态，应直接返回 `unknown`**。此项列为待修复缺陷（第 5 节 #7）。

### 4.3 对架构的直接含义

| 含义 | 说明 |
|---|---|
| 监控层无法按 SKU 分配纯 HTTP 资源 | 华为商城类页面必须渲染才能读状态 |
| 但按"会话"分配仍然成立 | 3 页/8.7 秒，单会话即可覆盖大量 SKU |
| 成本模型结论不变 | 监控按会话数扩容，执行 Slot 按峰值并发扩容，两者分开核算 |
| 渲染耗时是回流发现速度的上限 | 单页 2.9 秒中位 × 目标数 = 一轮全量检查耗时 |

## 5. 已修复的探针缺陷

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | `IP.*(限制\|封禁)` 正则过宽，中文常用词即可命中 | 把正常页面误报为风控拦截 | 收紧为 `IP 限制 / IP 封禁 / 禁止访问 / 拒绝访问 / Access Denied / 403 Forbidden` 等明确措辞 |
| 2 | `预约` 单词被当作预售信号 | Apple 的"预约到店"被判为商品预售 | 只保留明确的开售前置语（`接受预购 / 开始预购 / 预约购买 / 预约抢购 / 即将开售 / 订金 / 尾款` 等） |
| 3 | 未区分"被拦截"与"目标 URL 失效" | 二者都表现为页面不对，但排障方向相反 | 新增 `redirected_away` 状态，用重定向 + 路径深度 + 价格结构缺失 + 分类页特征词联合判定 |
| 4 | 风险词判定未要求上下文 | 正文任何位置出现即命中 | 保留但收紧（见 1），并把 `系统繁忙` 从风控信号移除（歧义过大） |
| 5 | `--rounds 2` 等空格分隔参数被解析为布尔 | CLI 全部数值参数失效 | 重写 `arg()` 支持 `--name=value` 与 `--name value`，并加 5 条单元测试（`test-args.mjs`） |
| 6 | 缺少发现真实 URL 的手段 | 手工编写 URL 导致首轮全部目标无效 | 新增 `--find-links <seedUrl>` 模式，从页面渲染出的 `<a href>` 中取真实链接 |
| 7 | **纯 HTTP 视角对低可见文本量页面过度自信** | 把 383 字的 JS 空壳判为"可纯 HTTP"（第 4.2 节） | **待修复**：可见文本 < 1500 字时不得据此判定库存，应返回 `unknown` |

## 6. 对审查报告的修正

**撤回**审查报告初稿中"苹果官网返回风控页/无法判定"的表述 —— 该结论来自分类器误判，事实是 URL 失效。

**升级**审查报告第 2.3 节的判断（Monitor 层纯 HTTP 轮询在强风控平台不成立）：证据等级由"线索"提升为**机制性结论** —— 华为商城禁用 JS 后可见文本仅 339 字 / DOM 833 KB，证明库存状态完全由客户端脚本注入。该节的架构建议（共享会话读渲染结果）获得实测支持。

**加强**第 8.1 节的设计要求：京东类平台的监控必须先持有登录态，profile 的持久化、独占租约与跨机归档不是可选项。

**加强**第 4.7 节（目标有效性自检）：华为旧款 URL 与苹果下架 URL 两例共同表明，目标静默失效会伪装成"平台不可监控"，适配器必须内置 URL 有效性自检并在失效时告警而非静默返回 `unknown`。

**新增**一条实现约束：判定逻辑必须与**可见文本量**挂钩 —— 可见文本过少时不得给出库存结论。这条同时防住"JS 空壳被误判"和"页面改版后静默误判"两种情况。

**更新**第 10 节未验证项：华为商城已从"未测"转为"已测得可判定"；京东仍待登录态验证。

## 7. 复跑指引

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = "$env:LOCALAPPDATA\ms-playwright"

# 步骤 1：发现真实商品 URL（苹果在售机型，只读页面链接）
node probe.mjs --find-links "https://www.apple.com.cn/shop/buy-iphone" --link-filter "buy-iphone/.+/.+"

# 步骤 2：登录一次京东，登录态存入 profile（会弹出浏览器窗口并保持 300 秒）
node probe.mjs --find-links "https://passport.jd.com/new/login.aspx" --headed --hold 300

# 步骤 3：华为单独复跑（已验证可判定，可随时回归）
node probe.mjs --config targets.json --only huawei --rounds 3 --interval 8 --verbose

# 步骤 4：全量复跑
node probe.mjs --config targets.json --rounds 3 --interval 8 --verbose
```

**步骤 2 必须人工完成扫码或账号登录，探针不会自动处理任何登录或验证**（红线三）。登录态写入 `chrome-profile/` 后，后续 headless 运行复用同一 profile。

## 9. 当前可信结论汇总

以下结论**可以直接用于阶段 4/5 的监控架构设计**：

```text
1. 共享浏览器会话顺序读取多商品页状态：可行
   证据：华为商城 3 目标 × 2 轮 6/6 可判定，零拦截，一轮 8.7 秒

2. 监控不能按 SKU 分配纯 HTTP 资源：已证
   证据：华为商城禁用 JS 后可见文本仅 339 字 / DOM 833 KB，库存状态由客户端脚本注入

3. 监控应按「会话」分配资源：成立
   证据：同上 —— 渲染是必要条件，但一个会话可覆盖多个目标

4. 京东类平台必须先持有登录态：成立
   证据：不带登录态的会话被重定向至登录页，读不到任何商品数据

5. 商品目标会静默失效，适配器必须自检 URL 有效性：成立
   证据：苹果目标指向已下架机型，重定向至导购页，被分类器一度误判为风控

6. 判定逻辑必须与可见文本量挂钩：成立
   证据：JS 空壳页面（383 字）会产生假阳性判定

7. 单页读取耗时量级 2～4 秒（headless 完整 Chromium，串行）
   → 100 个目标约 5 分钟一轮，这是回流发现速度的上限
```

以下**仍不可用于架构决策**：京东登录态下的风控反应、天猫与 NVIDIA 的可行性、并发承载量、选择器长期漂移率。
