### 次要修复（仍有效，非根因）

`huawei.user.js` v0.2.0 的 `document.body` 为 null 时 `appendChild` 抛错问题**确实存在**
（`page.addInitScript` 在 document-start 时机复现成功），已修：
`mountRoot()` / `waitForBody()` 兜底 + `main()` 先 `await waitForBody()`。
但它只是"若有脚本被执行就会踩"的隐患，**不是本次不执行的原因**——
因为在允许用户脚本开关打开前，脚本根本没跑到那一步。

用 `page.addInitScript`（等价 document-start，body 尚为 null）注入时抓到确切报错：

```
[PAGEERROR] Cannot read properties of null (reading 'appendChild')
```

原脚本 `ensurePanel()` 直接 `document.body.appendChild(panelEl)`（旧 128 行），**无任何兜底**。
虽然声明了 `@run-at document-idle`，但油猴 5.5.1 是 **Manifest V3** 架构
（manifest 里权限为 `userScripts` + `host_permissions: <all_urls>`），
在商品页这类快速导航场景下 document-idle 触发时 body 偶尔仍为 null。
一旦抛错，异常冒到 IIFE 外 → 整个脚本死掉 →
**表现为「面板完全不出现 + 油猴图标红叉」，且没有任何日志提示**，极难定位。

这也解释了为什么连 5 行的自检脚本都没反应 —— 同一个坑。

**修复（已落地，v0.2.0）**：
1. 新增 `mountRoot()`：返回 `document.body || document.documentElement || null`
2. 新增 `waitForBody(timeoutMs=5000)`：轮询等 body 就绪
3. `ensurePanel()` 用 `root.appendChild`，root 为 null 时返回 null 而非抛错
4. `log()` 里 `if (!p) return;` 兜底
5. `main()` 开头 `await waitForBody();` 再 `ensurePanel()`
6. `main().catch()` 再包一层 try，异常处理自身失败时兜底到
   `document.body || document.documentElement`，绝不出现"未捕获的 Promise 拒绝"

**验证结果**：document-start 时机注入 → 面板出现 ✓、阶段"等待登录" ✓、脚本自身零错误 ✓。
（注意：此验证是在 Playwright 里注入，绕过了油猴，所以能证明代码健壮性，
不能证明油猴侧已授权——油猴侧仍需用户开 Q209 的开关。）

### 踩过的坑（累计）

- **写用户脚本必须以 `// ==UserScript==` 开头、`// ==/UserScript==` 结尾**。
  漏掉整块 → 油猴判「无效」，提示「URL 不匹配」，而真实原因是没有匹配规则，报错有误导性。
- **用户脚本里绝不直接用 `document.body.appendChild`**。
  必须 `(document.body || document.documentElement)` 兜底，并配合 waitForBody。
  否则 document-start 时机静默死掉，面板不出现 + 图标红叉，无日志可查。
- Chrome match pattern：`?prdId=...` 查询串**不参与**匹配，只比对 scheme+host+pathname。
  `item.vmall.com/product/<prdId>.html` 这种老式路径**不被** `/product/comdetail/*` 覆盖。
- **Playwright 里模拟 `GM_xmlhttpRequest` 不能用页面内 fetch**：
  `https://item.vmall.com` → `http://127.0.0.1:3100` 被 CORS 拦
  （"Permission was denied to access the loopback address space"），
  脚本会在 `loadConfig()` 短路、掩盖真实问题。必须用 `page.exposeFunction` 交 Node 发。
- `page.evaluate` 里对象属性名不能带 `#`（如 `在#prd-detail内:`）→ SyntaxError，
  得写成 `'在prd-detail内':`。
- 解析油猴 metadata 时 `@match`/`@grant`/`@connect` 是**多值**，
  存进普通对象只保留最后一个 → `.every is not a function` 之类误判。
- 临时测试脚本要放项目目录内（依赖 node_modules），放 /tmp 会 ERR_MODULE_NOT_FOUND。
- 本机 `reg.exe` 在程序黑名单里，查询注册表会被拦；PowerShell 工具不回显输出。
  查 Chrome 信息改用读 `%LOCALAPPDATA%\Google\Chrome\User Data\Local State`（JSON）。

```

      name（完整规格名）/ price / status / buttonMode / limitedQuantity
```

**三个必记的坑：**

1. **`extendList` 就是延长宝/保障服务**，每个 sbom 各挂一份：

## ★ 本轮踩的坑

1. **`deepMerge` 会污染配置顶层**：`POST /api/config` 传 `{productUrl, sbomCodes}` 时，
   顶层没有这两个 key → 合并后**写到顶层去了**，产品的 `sbomCodes` 没变。
   勾选看着成功、实际没生效。
   → 新增专用接口走「读整份 → 改一项 → 整份写回」，不用局部合并。
   `products` 是**数组**，局部合并会整体替换，也走专用接口。

2. **控制台 HTML 无条件缓存** → 改完文件刷新页面没变化，白排查。
   → 改按 `mtimeMs` 判断重新读。

3. **本机 `curl` 默认走代理**，访问 `127.0.0.1:3100` 会报
   `upstream connect failed` / 拿到别的响应。**必须加 `--noproxy '*'`**。

4. **后台起 node 服务要用 `run_in_background: true`**，
   `(node ... &)` + `sleep 2` 的写法在 shell 退出时会把进程带走（HTTP=000）。

5. **browse skill 在本机坏了**：`Failed to parse URL from http://127.0.0.1:47413http://...`
   （URL 拼接重复），`status` / `restart` 都一样。
   → 截图改用项目自带的 Playwright 脚本 `grab-probe/shot-console.mjs`（更快更可控）。

## ③ 多账号并发 —— 不需要指纹浏览器 ★★ 有实测数据

**关键：Playwright 的 `browser.newContext()` 天然就是登录态隔离的**，
一个 Chromium 进程能开 N 个 context，各自独立 Cookie/localStorage/sessionStorage。
用户"一个浏览器只能登一个账号"的顾虑在普通浏览器上成立，在 context 层不成立。

### 实测数据（本机 Ryzen 5 5600 / 16G / headless）

| 账号数 | 内存 | 边际/个 | Chromium 进程 | 事件循环延迟 |
|---|---|---|---|---|
| 10 | 218 MB | 21.8 MB | 13 | 12ms |
| 54 | 1166 MB | 21.6 MB | 57 | 14ms |
| 120 | 2562 MB | 21.4 MB | 123 | 11ms |

**每账号约 21MB，线性无拐点。120 个账号 2.5GB。**

隔离验证：ctxA cookie=`sid=ACCOUNT_A`，ctxB cookie 为空 → ISOLATED ✓
反面：同 context 内多 page **共享** cookie jar → 单 context 装不了多账号（这正是 context 不可替代的原因）

### ★ 最大的坑：同一 userDataDir 不能双开（不报错，更难查）

```
两个进程同开一个 userDataDir：
  内存态各自独立（A 看到 ACCT_A、B 看到 ACCT_B），看似没问题
  但磁盘 profile 并发读写：
    addCookies  4ms → 1458ms   （慢 364 倍）
    close()     1277ms → >10s 挂死
```
**Windows 上 Chromium 不对 userDataDir 做硬锁**，双开不立刻失败，
而是随机 IO 竞争/句柄争用/关闭挂死 —— 可能在抢购那一刻才发作。
→ 铁律：一账号一独立目录，同刻只能一个进程打开。

### 时刻对齐实测

- `Date.now()` 步进 0~1ms；`setTimeout` p50=6ms max=16ms（不够准）；**页面内忙等**最准
- 8 个进程忙等同一绝对时刻：drift **全部为 0**
- 同时开火的服务端到达离散：10 账号 4ms / 30 账号 17ms / **50 账号 32ms**

### CDP 并发

吞吐 10 context 时饱和约 1200 req/s；往返 p95：1→1.1ms、10→5.2ms、30→18.1ms、50→37.4ms

### 架构结论

```
单 Node 进程 + 单 Chromium + N 个 newContext（不要多进程，每 persistent = 一个独立 Chromium 实例）
profiles/<账号>/ 一账号一目录，仅用于「登录态维护」
开抢时不用 persistent context（有目录锁问题），
  改为导出 storageState(JSON) → newContext({ storageState }) 批量建
  已实测可完整还原 cookie + localStorage
5 个账号并行各用独立目录：1.85 秒全部就绪 ✓
```

**为什么不推荐指纹浏览器**：它解决的是"跨设备指纹一致/伪装成不同设备"；
本机多账号要的是**登录态隔离**，context 就够了。指纹伪装属风控对抗，不在本方案边界内。

### ③ 已实施的优化：自适应轮询间隔

`grab/huawei.user.js` 主循环改动：
```js
const pollMs    = config.limits?.pollIntervalMs    ?? 3000;   // 平时
const pollHotMs = config.limits?.pollIntervalHotMs ?? 150;    // 临售/开售后
const hotWindowMs = config.limits?.hotWindowMs     ?? 10000;  // 提前多久切快查
const pickInterval = () => {
  if (!saleAt) return pollHotMs;                        // 不定时 → 一直快查
  if (Date.now() >= saleAt - hotWindowMs) return pollHotMs;
  return pollMs;
};
// 快查阶段不加抖动：抖动是针对网络请求的顾虑，这里纯读本地 DOM，抖了只是丢精度
await sleep(useHot ? pollHotMs : jitter(pollMs, jitterRatio));
```

**关键论证（已写进 README 第四节）**：readStockState() 只读本地 DOM，**一个网络请求都不发** ——
提高检测频率不增加任何平台侧可见流量，纯粹本机 CPU 开销（6ms/轮 × 150ms ≈ 4%）。

## ★ 排查出并修复的真 bug：控制台白屏

**症状**：面板打开是空的（0 商品卡片、0 行 SKU），报

## 教训清单

- **`$('#x')` vs `$('x')`**：项目里 `$` 是 getElementById 的包装，**传纯 id**。
  另一会话按 querySelector 习惯写了带 # 的，导致全线失效且报错难定位。
  → 以后看到 `$('#` 就要警觉。
- **测要和错的一致**：我手动复现用的是无 # 版本，所以一直"复现不出来"。
- **顶层 DOM 绑定必须有防御**，否则一个元素缺失会让整段脚本不执行（白屏、无日志）。
- 服务"failed"通知不等于故障 —— 先看是不是被人重启替换了（查端口 + health）。
