# 华为抢购全链路说明与提速方案

**日期**：2026-10-08 ｜ **依据**：`platforms/huawei/cdp-rush.mjs` 当前代码 + 当日实测（`verify/bench-internal-chain.mjs`）
**一句话总览**：一条主链「准备 → 定时刻 → 值守 → 预开 → 热窗监听 → 触发 → 确认页 → 提交 → 读结果」，两套触发器（内部通道 ∥ 点击通道）并行互兜，一条副链（回流监控）收拾残局。

---

## 一、逐步拆解：每步做什么、依赖谁、花多久

### 第 0 段：起飞前（一次性，不参与和别人的竞速）
| 步 | 做什么 | 耗时 |
|---|---|---|
| 白名单闸门 | 核对商品列表+勾选规格；不在列表 → 不开窗口、直接跳过 | <1ms |
| 起窗口 | 复用专用 Chrome（已有则不重启）；连 CDP、装拦截(R1/R2)、订阅确认页事件(R3) | 复用 1~2s / 冷启 3~10s |
| 页面就位 | 进商品页、等加载与水合、核对"已选"规格（防抢错） | 2~5s（页面加载，排除项） |
| 风控/登录 | 以 queryUserInfo 接口为准判登录；未登录就等人 | 50~200ms |
| 价格上限 | 读页面价格，超上限不执行（可选） | ~10ms |

### 第 1 段：定时刻（一次性 ~1~2s）——决定"什么时候出手"
- 官方接口拿开售时刻（`queryRushbuyInfo.startTime`），拿不到用配置 saleAt 兜底；
- 校时：5 样本取中位数算"本地钟 vs 服务器钟"偏差 offset；热窗前（T0-3s）再精校一次（3 样本）；
- 输出：`triggerLocalMs = 服务器T0 + offset`（换算到本地钟）。
- 关键：全链所有"到点出手"都靠这条时间轴；它的误差 = 提前或滞后出手的系统偏差。

### 第 2 段：值守（派发太早时；分钟级，低功耗）
- 每 30s 拍一次哨兵：风控 / 登录掉线 / 页面规格被切走；
- 每 5 分钟做一次保温（真实鼠标移动+滚动，不碰任何请求）；
- 到 T0-90s：刷新商品页做"最终就位"（页面加载）。

### 第 3 段：预开确认页（T0-60s；目前只有"现货+定时"吃得到）
- 做什么：趁按钮已是解锁态，先把"确认订单页"开成草稿放着（不提交）；
- 收益：把"点击→确认页加载"的 3~5 秒从关键路径上挪走——全链最大的结构性提速；
- 自门控：真定时商品按钮锁着开不出 → 自动回常规流程，零副作用。

### 第 4 段：热窗监听（T0-3s 起；每轮 51~65ms）
- 一轮只做一件事：一次快速检测（先直查按钮锚点，解锁后再读全页信号）；
- 与此同时两条推进线都在动：内部 fire（每 ≥300ms 一次）+ 点击通道（看到可点按钮就点）；
- 出手闸门：T0-500ms 之前不动作（防现货提前出手；也是给点击路径的提前量）。

### 第 5 段：触发购买（把"想买"变成"进了确认页"）
- 内部通道：CDP 7 跳从按钮闭包里取出 `Yo()` / `goBuy()` 直接调（实测 4.6ms），页面自己开确认页；
- 点击通道：CDP 派发真实鼠标事件（实测 47ms，含 30ms 固定睡眠），isTrusted=true；
- 两条道并行、谁先成谁算；确认页一出现由浏览器事件瞬时感知（R3）；
- R1 拦截把页面收到的倒计时提前 300ms 归零 → 按钮提前解锁。

### 第 6 段：提交订单（真模式；把"草稿"变成"订单"）
- 内部提交：fiber 上找 `handleOrderSubmit` 直接调（实测 0.5ms）；按钮还没挂载就每 300ms 等；
- 兜底点击：滚动 → 睡 300ms → 重取坐标 → 点击（实测合计 352ms）；
- 只发一发、绝不重试（防重复下单）——所以"第一发"的时机必须对（见 P1）。

### 第 7 段：读结果（500ms/拍 × 24 = 12s 上限）
- 读到订单号 → 成功；出现收银台 → 订单已建；缺收货地址 → 转人工；读不到 → 标记待人工；
- 支付永远人工，脚本不碰。

### 第 8 段（副链）：回流监控（没抢到后守漏）
- 双信号：每 15s 问一次接口（字段一变立刻查页面）+ 每 30s（前 40 分钟）/60s 刷新页面看按钮；
- 捕获回流后走与正抢完全相同的触发链路。

## 二、依赖与先后顺序（谁卡谁）

- **硬串行**（缺任何一步全停）：白名单闸门 → 专用窗口 → 登录 → T0 已知 → 出手闸门开 → 触发购买 → 确认页 → 提交 → 读结果；
- **并行冗余**：内部通道 ∥ 点击通道，互相兜底；R1/R3 是放大器（提前解锁 + 瞬时感知）；
- **串联三连（决定成败）**：触发 → 确认页 → 提交。其中"确认页"一步吃 3~5 秒——预开就是专为砍它而做；
- **失败分支**：缺货/超时 → 回流监控；出现验证码/风控 → 立刻停车转人工（任何阶段）。

## 三、耗时总表与真正的瓶颈

### 实测/静态耗时（单位 ms，p50）
| 环节 | 耗时 | 说明 |
|---|---|---|
| 内部购买全链 | 4.6 | 7 跳 CDP 调用链，p90 8.6 |
| 内部提交（已挂载） | 0.5 | 单次 evaluate |
| 兜底点击 trustedClick | 47 | 含 30ms 固定睡眠 |
| 热循环检测节拍 | 51~65 / 轮 | 50ms 睡眠 + 1~13ms 检测 |
| 解锁 → 点击出手 | ~110 | 节拍 + 点击合计（压线） |
| **提交兜底完整链** | **352** | 300ms 硬睡 + 滚动 + 点击 |
| **NO_ENTRY 降级前重试** | **1800** | 6 × 300ms 才回落点击 |
| **点击后无确认页盲等** | **30000** | 等满才重试 |
| **内部失效判定** | **60000** | 200 次 × 300ms（文档写的 10s 是旧数字） |
| 确认页加载（页面自身） | 3000~5000 | 排除项，但真实影响成交（预开针对它） |

### 真正的瓶颈（按对"抢到"的伤害排序）
1. **确认页加载 3~5s（结构性问题）**：预开已解决"现货+定时"，纯定时商品目前吃不到 → 优化实验 P1-9；
2. **内部 fire 300ms 节流**：5ms 的活却 300ms 才发一次，相位不好白等一拍 → P0-1；
3. **提交兜底链 352ms + NO_ENTRY 前摇 1.8s**：真模式若走兜底就比别人慢 0.3~2s → P0-2；
4. **时钟/闸门精度 ±几十 ms**：决定"早一步还是晚一步"→ P0-5 / P1-8；
5. **非瓶颈（别在这花力气）**：CDP 单跳 0.5ms、结果轮询、状态检测本身。

## 四、优化方案（提速 × 风控，一起谈）

**总原则：所有力气花在"服务器看不见的地方"。**
- 本机行为（DOM 查询 / CDP 调用 / 内部函数 / 改写收到的响应）：服务器完全不可见，提速不限速；
- 服务器可见面（页面自己发出的请求）：保持人类节奏，只动"时间对齐"，不加频率。
- 结论：提速与避风控**基本不冲突**，冲突只集中在两处——**提交重试**与**刷新频率**，下文单列取舍。

### P0：纯本地提速（风控零成本，随时可做）
1. 内部 fire 节流 300ms → 50ms；命中/确认页已出现后停止重复发火（避免多开草稿页）；
   【2026-10-08 已实施：改为控制台面板项「内部喊话节奏」，默认 50；"命中后停发"未做（评估：确认页去重已覆盖，保持最小改动）】
2. 提交兜底：300ms 硬睡 → 80ms；NO_ENTRY 重试 6 轮 → 1 轮（1.8s → 0.3s）；
3. 点击后无确认页盲等 30s → 5s（点击本身无副作用，快重试安全）；
4. 确认页挂载探测 300ms → 60ms 节拍（提交更早发出）；
5. 校时加强：5 → 11 样本、取"最小 RTT 样本"、热窗前复校；
6. 内部失效判定 200 次 → 10s 时间窗（与文档一致）；
7. 热窗最后 1 秒用忙等（消 Windows 定时器 ~15.6ms 抖动）。

### P1：赛点时序修正（涉服务器可见面，必须演练验证）
8. **预开提交对准 T0**：现在 T0-500ms 就发（太早，反而像异常）；改为"T0 减去实测网络延迟"，
   让请求在 T0±ε 到达服务器；失败确认后再补发（上限 2~3 发）；
9. **大 lead 预开实验（最高收益/最高不确定）**：把 R1 的 leadMs 从 300ms 加到 3~5s，
   让【纯定时商品】按钮也提前解锁 → 也走预开，把 3~5s 页面加载全挪出关键路径；
   实验前要验证：提前的"进入确认页"请求会不会被服务器拒、确认页放 5 秒会不会失效；
10. 提交失败条件重试：仅在页面出现明确错误信号时补发，间隔 ≥100ms，见订单号立即停。

### P2：微优化
11. 去掉每轮的 legacy 探测（省 0.5ms）；窗口提前 5 分钟起好（把冷启动挪出赛点）。

### 红线（任何情况都不做）
- 不构造/重放订单请求、不绕验证码、不自动支付；
- 不加密回流刷新（30s 是底线）、不盲目多开账号（要加就配独立出口）；
- 不在 T0 前多次发提单（异常特征，反而害自己）。

### 取舍矩阵
| 动作 | 提速收益 | 风控成本 | 结论 |
|---|---|---|---|
| 内部节流 300→50 | 高（0~300ms → 0~65ms） | 零（纯本机） | 已实施（面板可调，默认 50） |
| 提交兜底提速 | 中（352→160ms） | 零/低（点击是本机事件） | 立刻做 |
| 预开提交对准 T0 | 高（消除 -500ms 误差） | 负（更不像异常） | 演练后做 |
| 大 lead 预开 | 最高（3~5s） | 未知（提前请求特征） | 先单槽实验 |
| 提交条件重试 | 中高（防整槽报废） | 低（2~3 发≈人类急点） | 演练后做 |
| 回流监控加密 | 中 | 高（请求频率特征） | 不做 |
| 多账号+多 IP | 高 | 高（关联封号风险） | 不做 |

## 五、演练验证清单（优化落地前逐条验证）

1. 预开提交时机：真场次盯日志"到点：在预开的确认订单页上直接提交"，看服务器接受窗口；
2. 大 lead 预开：单槽把 leadMs 临时调 3000，看"确认页能否开、进入请求是否被拒、5s 后提交是否仍有效"；
3. 提交条件重试：先在演练模式验证"错误信号识别"不误判，再放开真模式；
4. P0 各项改动做完后跑 `verify/bench-internal-chain.mjs` 回归，确认数字达标。

## 附：人话对照表（本文术语翻译）

| 术语 | 人话 | 一句话解释 |
|---|---|---|
| T0 | 开售的准确时刻 | 例如 10:08:00；"T0-60s" = 开售前 1 分钟。全文拿它当尺子 |
| 预开 | 提前把确认订单页打开摆好 | 开售前 1 分钟先打开"确认订单页"放着（只是草稿、不算下单）；开售一到直接按提交，省掉页面加载的 3~5 秒 |
| 内部 fire | 绕过鼠标、直接"喊"按钮干活 | 按钮背后有一段现成的干活代码；点按钮=用鼠标去按它，"喊"=直接让它跑（快约十倍）。fire 只是代码里的代号 |
| 节流 | 限速规定 | "每 300 毫秒才准喊一次"；可喊一次其实只要 5 毫秒 → 按钮刚亮时可能白等小半秒 |
| 提交兜底链 | 提交的"备胎方案" | 主办法喊不通时改用鼠标滚过去点一下；这条路里有一段固定 300 毫秒的干等（合计 352 毫秒） |
| leadMs / 大 lead | 提前量 | 把页面倒计时"骗早"多少毫秒；现在骗早 0.3 秒，实验想加到 3~5 秒好让定时商品也能预开 |
| 热窗 | 开售前的紧盯时段 | 开售前 3 秒起进入最高频盯守（每轮约 50~65 毫秒看一眼） |
| 闸门 | 允许出手的开关 | 开售前 0.5 秒才打开；之前按钮再亮也不动手（防现货误触） |
