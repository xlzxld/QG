## 0. 先读这一节：人话对照表

| 术语 | 一句话人话 |
| --- | --- |
| 桥接服务 / 控制台 | 你电脑上那个常驻小服务（端口 3100）＋网页控制台，管配置、派任务、收结果 |
| 执行面 | 真正去点手机、点网页的那一侧。目前只有"电脑浏览器"，本方案新增"安卓手机" |

| 提前量 | 故意比开售时间早几毫秒动手，抵消"点击→请求到达服务器"路上的耗时 |
| 任务单 | 一条完整的指令包：抢哪个平台、哪个目标、几点开抢、什么规格、提前量多少 |
| 白名单 | 既有硬规则：控制台商品列表里的才操作，不在列表里的碰都不碰 |
| 标定 | 上岗前先做实测：先量一遍、记下来，再按量出来的数干活 |
| 彩排 | 用不紧张的目标（冷门演出、低价商品）完整走一遍流程，止步支付页 |
| 投屏接管 | 手机画面实时投到电脑上，人用鼠标直接操作手机（对付滑块验证等） |
| 无障碍服务 | 安卓给自动化开的一扇门；AutoX 靠它读页面元素、执行点击 |
| Shizuku | 不刷机、不 root，给脚本借用 ADB 级别的权限（官方调试接口路线） |
| 深链 | 应用专属链接，点了直接跳进 App 的指定页面（省去首页→搜索→点选的绕路） |
| 模拟器 / 真机 / 靶机 | 电脑上模拟的手机 / 真实手机 / 专门用来"试探检测强度"的旧手机 |

## 1. 结论先行

**① 通讯与调度：不用消息总线（WebSocket/MQTT），用"USB 线内跑 HTTP 长轮询"。**
一根线 + `adb reverse` 把手机的 `localhost:3100` 直接接到电脑桥接服务上（电脑仍只监听本机、不向局域网开任何口）。手机每隔几秒问一次"有任务吗"，拿到任务单就先**存到手机本地**；**到点那一下完全不依赖网络和电脑**——击发靠手机自己的钟。为什么：抢购是毫秒级的，网线和电脑都不可信；只有"任务提前送达 + 本地击发"才稳。任务在开抢前几分钟就发下去，通讯偶尔抖动不影响结果。

**② 一键拉起：控制台一个按钮，背后是一段"分段自检 + 坏了能降级"的 adb 序列。**
体检设备 → 唤醒解锁 → 检查/安装 Agent → 建立通道 → 启动脚本 → 脚本回连报到。共 10 步，每步成功与否都上报；任何一步失败，控制台立刻红字报警并给出降级动作（比如提示你"手动把页面就位"）。**它必须先在"标定清单"上全项实测通过，才允许上真场次**；没过之前用"人工就位、脚本只管击发"的兜底模式照样能打。

**③ 模拟器：正式抢购不用，只用来开发和彩排。**
三类原因：平台风控能识别模拟器（系统属性、设备节点、传感器全零、触控特征、指令转译时延）；ARM 转译有性能损耗；模拟器的控制权终究是"别人的壳"（云手机同理）。开发彩排：Windows 本机用 Android Studio 自带模拟器或 docker-android 即可；redroid 容器方案留给将来有 Linux 机器时。**真机也不是免疫的**——还要管住"自动化行为纪律"（见 §5.2），否则真机照样吃滑块。

**与下一阶段的适配性：适配（有条件）**。大麦/淘宝/京东的 App 端正是这三个渠道的主战场，方案结构和你现有系统（白名单、派发、结果回传、体检）天然同构，单机 → 多机不用重构。条件就是审查给出的 5 条硬前置（§10.5），以及 3 项待拍板（文末）。

## 3. 通讯与调度机制（重点一）

### 3.1 通道选型：为什么是"adb reverse + HTTP 长轮询"

| 方案 | 长什么样 | 优点 | 为什么不选 / 何时再选 |
| --- | --- | --- | --- |
| **A. WebSocket 实时总线** | 桥接新开 3210 端口跑 WS，手机连上来 | 消息实时、可双向推 | ❌ P0 不用：击发不依赖实时（任务提前几分钟已送达）；新增端口/心跳/重连/幂等全是净增复杂度；且一旦为多机"开局域网"会撕开现有"仅 127.0.0.1、无鉴权"的边界（安全回归）。**留作 P2 备选**：只在"多机 + 需要秒级推送"时评估，且必须先加设备令牌 + IP 白名单 + 关掉通配 CORS |
| **B. adb reverse + HTTP 长轮询** ✅ | `adb reverse tcp:3100 tcp:3100`；手机访问自己的 `127.0.0.1:3100` 即直达电脑桥接 | 零新端口、零新依赖（桥接现有 HTTP 直接用）；USB 内跑，不经 WiFi；断线重连简单 | 选中。优点恰好是"最少活动件" |
| **C. MQTT / 消息队列** | 中间加 Broker | 跨网段、NAT 友好 | ❌ P0 明确不做：1~3 台设备场景属于过度设计；留待"设备不在同一局域网"时再评估 |

> 大白话：`adb reverse` 就像给手机插了一根"隐形网线"，手机以为在访问自己，其实是在访问你电脑上的桥接服务。电脑仍然只对本机开放，安全边界不扩大。

**通道细节（照抄即可用）**：

```bash
# 体检
adb devices                                   # 设备在不在
adb -s <序列号> shell getprop sys.boot_completed   # 系统起没起完
# 建立通道（每次 adb server 重启/设备重插后都要做，桥接会自动补）
adb -s <序列号> reverse tcp:3100 tcp:3100
# 验证：手机上访问 127.0.0.1:3100/health 应返回 ok
adb -s <序列号> shell "curl -s http://127.0.0.1:3100/health" 2>/dev/null || true
```

**心跳与保活**：Agent 每 5 秒发一次心跳（POST `/api/device/heartbeat`）；桥接超过 30 秒没收到 → 控制台黄灯（"失联"）→ 红字告警。`adb reverse` 是易失的（拔线、adb 重启、设备重启都会丢），桥接侧做一个"哨兵"：发现设备在线但通道探测失败，自动重发 reverse（幂等，可放心重复发）。

### 3.2 消息与数据格式

全部是普通 JSON。核心四类：

```jsonc
// ① 心跳（Agent → 桥接，每 5 秒）
{ "type": "heartbeat", "deviceId": "dv-7f3a…", "state": "idle|armed|firing|done",
  "taskId": null, "ts": 1791449000123 }

// ② 取任务（Agent 长轮询桥接；无任务则挂起最多 25 秒后返回 204）
GET /api/device/task?deviceId=dv-7f3a…
→ 200 { "type": "task", "taskId": "t-20261015-2000-damai-1", "platform": "damai",
        "fireAtEpochMs": 1791500000000,     // 开售绝对时刻（平台服务器时间口径）
        "leadMs": 40,                        // 提前量（标定得来，见 §3.4）
        "target": { "kind": "show", "url": "https://detail.damai.cn/item.htm?id=…",
                    "session": "10.15 19:30", "priceText": "内场 980",
                    "viewers": ["张三"] },
        "actions": "damai-default",          // 端侧流程编号
        "whitelistHash": "8b2c…",            // 白名单快照指纹（离线校验用，见 §7.2）
        "expireMs": 1791500600000,           // 过期即作废，防重放
        "dry": false }

// ③ 事件（Agent → 桥接，异常/中间态）
{ "type": "event", "taskId": "…", "event": "risk_challenge|page_mismatch|sold_out|retry",
  "detail": { "screenshot": true }, "ts": 1791500000234 }

// ④ 结果（Agent → 桥接；内部即写入 <平台>.results.jsonl，沿用现有格式扩展）
{ "type": "result", "taskId": "…", "outcome": "ordered|no_stock|risk_challenge|unknown|failed",
  "platformOrderNo": "…", "evidence": "订单页可见『订单提交成功』+ 我的订单可查",
  "seq": 3, "ts": 1791500000567 }
```

**三条硬规矩（踩过坑的地方）**：

1. **结果先存本地再上报**：手机端 outbox（本地 JSONL），上报成功才清；断线重连自动重传。桥接按 `taskId + seq` 去重后落盘——电脑盘忙、桥接重启都不丢结果，也不会重复落盘。
2. **幂等防重复下单**：同一个 `taskId`，端侧记"已击发"标记，重启/重连/重派都**拒绝二次击发**；过期任务单直接作废。桥接侧把现有"平台级 409"细化到"任务级"。
3. **读不到就报 `unknown`，不许编**。结果字段固定为上面五个枚举，`ordered` 必须以可核验凭证为准（订单号或"我的订单"可查），文案信号只作辅助。判定不确定 → 报 `unknown` + 告警人工确认，**不自动重试、不自动释放**。

### 3.3 时序（从彩排到收兵）

```
时间轴                电脑（桥接/控制台）                     手机（Agent）                平台服务器
────────────────────────────────────────────────────────────────────────────────────────────────────
T-30 分钟   设备页点「彩排/就位」→ adb 序列（§4）
            └─ 通道、脚本、回连握手完成 ─────────────► Agent 在线、心跳 5s
T-10 分钟   推送任务单（长轮询立达） ────────────────► 存本地 outbox、校验白名单快照
                                                    预热：打开目标 App 页面、展开票档
T-1 分钟                                            对时：直连平台采样 N 次（取最小 RTT 样本）──► 采样
                                                    复核页面身份（是目标场次/商品吗？）
T-40 毫秒                                           最后 50ms 用"单调钟"死等（不受钟表跳变影响）
T0-提前量ms                                         击发：无障碍点击（多层查找降级）
                                                    点击→App 发请求 ─────────────► 到达服务器
T+0~3 秒                                            读页面：成功凭证 / 缺货 / 滑块
            ◄──────────── 结果先存本地、再上报 ────┘
T+3 秒      落盘 + 去重 → 控制台显示「最近结果」       （若滑块：蜂鸣 + 投屏人工接管 §7.3）
T+~30 分钟  对账提醒（订单需在时限内支付）
```

### 3.4 时钟对齐（这一段决定毫秒级胜负）

- **权威钟 = 平台服务器**，不是电脑、不是手机。手机直连平台采样，电脑不参与基准。
- **采样方法**：连采 5~10 次，取**最小往返耗时（RTT）的那一次**的偏差作为采用值（不是取中位数——中位数会把大 RTT 样本的系统偏置留下）。开抢前 1 分钟**复采一次**做修正。
- **京东**：社区脚本已长期使用 `api.m.jd.com` 的对时途径（`functionId=QueryNowTime` 或响应头里的毫秒时间戳），精度目标约 0.1 秒级。P0 需复测选定一种（接口字段可能变）。**淘宝/大麦**：没有公开对时接口 → 两条路：① 抓平台接口响应里自带的毫秒时间字段（P0 标定项）；② **相对标定法**——不打"绝对时刻"，改为"用平台是否接受点击"扫出最佳提前量（演练阶段摸出 `leadMs`）。
- **提前量 `leadMs`**：点击到请求到达服务器有 40~60 毫秒的路程（社区京东实战区间），所以要比开售时刻**提前一点点**动手。初值 40ms，按 §8 的"标定"逐平台/逐网络/逐机型实测校准，写进任务单。
- **末段等待必须用"单调钟"**：最后几十毫秒死等要用 `System.nanoTime()` 级别的单调计时（AutoX 里可通过 `java.lang.System.nanoTime()` 拿到），**不要用 `Date.now()` 墙钟**——等待窗口内一次系统校时跳变会让击发漂移甚至漏发。这是审查抓出来的要点，已写进设计。

### 3.5 状态机（防呆，防重复）

```
idle ──收到任务单──► armed ──(T-1min 对时+页面校验)──► primed ──(到点)──► fired
  ▲                    │                                  │
  │                    └── 校验失败 → rejected（告警，不击发）
  │                                                       ├─► ordered      （凭证在手）
  └──完成/超时─────────── done ◄── 上报─────┐              ├─► no_stock     （缺货/售罄）
                                            ├── unknown ◄──┤
                                            │   （必须人工确认，不自动重试）
                                            └── risk_challenge（蜂鸣+投屏，人工滑）
```

**换绑即重置**（沿用现有铁律）：设备换了平台/目标 = 一个事件 → 清掉预热就位状态、旧任务单作废、控制台旧结果不再展示。

## 4. 一键拉起的实现路径（重点二）

### 4.1 十步链路（控制台一个按钮 → 这里全自动）

| # | 步骤 | 命令/动作 | 失败时怎么办（降级） |
| --- | --- | --- | --- |
| 1 | 设备体检 | `adb devices`、`getprop sys.boot_completed` | 重插/换线提示；黄灯 |
| 2 | 唤醒 + 解锁 | `input keyevent KEYCODE_WAKEUP`；`wm dismiss-keyguard` | 若有 PIN 锁 → 提示"充电时不锁屏"设置（标定项） |
| 3 | 屏幕纪律 | 充电常亮、关动画（`settings put global window_animation_scale 0` 等三项） | 一次性整备，写进设备清单 |
| 4 | Agent 版本检查 | `pm list packages` / 版本比对 | 缺失或旧版 → 推 APK 安装（标定项：MIUI 等需人工点确认） |
| 5 | 建立通道 | `adb reverse tcp:3100 tcp:3100` | 幂等重试 3 次；仍失败 → 报"通道故障" |
| 6 | 启动脚本 | `am start -n <AutoX包名>/<RunIntentActivity> -d file:///sdcard/qg/rush-agent.js -t text/javascript`（组件名已列入标定清单，实测后固定） | 启动意图失败 → 降级②：AutoX 悬浮窗手动点运行；再失败 → 人工就位模式 |
| 7 | 脚本回连报到 | Agent 发心跳（§3.2） | 10 秒未回连 → 红灯，提示看手机（可能无障碍被系统关） |
| 8 | 下发任务单 | 桥接推送（长轮询立达） | 心跳正常即可重推；过期作废 |
| 9 | 预热就位 | 深链直达 / PC 侧 adb 直驱导航 / 人工手动都行（§4.4） | 三种方式互为兜底 |
| 10 | 待击发 | 对时 → 本地死等 → 击发 | 全程由手机负责；电脑此刻断线也不影响 |

### 4.2 "分段自检"是这套链路的灵魂

审查结论里说得很直接：这 10 步里任何一步都可能断，**好在全部发生在开抢前的几分钟，不是赛点**。所以策略是：

- 每步都有明确的"成功判据"（不是只看命令退出码）；
- 任一步失败 → **立即报警 + 给降级动作**，绝不静默；
- 降级链：全自动 → 半自动（悬浮窗手动启动）→ 人工就位 + 脚本击发 → 纯人工。**赛点（击发）永远在手机本地，与上面链路是否完美无关。**

### 4.3 标定清单（P0 必须先过的 8 项实测，缺一不可）

| # | 项目 | 验什么 |
| --- | --- | --- |
| 1 | intent 组件名 | `dumpsys package org.autojs.*` 找 RunIntentActivity 的真实包/类名（各分支版本不同，社区样例来自 v6 时代，v7 以实测为准） |
| 2 | 存储权限 | Android 11+ 需给 AutoX `MANAGE_EXTERNAL_STORAGE` 才能读 `/sdcard` 脚本；实测推送+运行 |
| 3 | 锁屏策略 | "充电时不锁屏" + 唤醒键测试；不可自动解锁就打红灯 |
| 4 | 厂商省电 | AutoX 和三个 App 加电池白名单；实测挂 30 分钟不被杀 |
| 5 | 深链表 | 大麦/淘宝/京东各:目标页能不能直达、直达后落在哪一页（京东 BP 链路 `p.m.jd.com/norder/order.action?wareId=…&enterOrder=true` 已有社区实证，另两个待实测） |
| 6 | 无障碍覆盖率表 | 三平台关键页（详情/确认订单/观演人弹窗/购物车结算）:关键按钮有没有可读节点、点击成功率。自绘 UI 页面可能没有节点 → 记为"只能坐标+人工兜底" |
| 7 | 对时源 | 各平台可用时间源 + 采 20 次看偏差分布（min/中位/max） |
| 8 | 提前量 | 非抢购演练：量"点击→请求发出/被接受"耗时分布 → 得 `leadMs` 初值 |

**8 项全过的平台，才允许开"自动击发"**（§10.5 条件 5）。没过 = 该平台先只做监控（P0a）。

### 4.4 P0 双模式（审查采纳项）

**模式甲（全自动）**：上面 10 步全自动，用于 `leadMs` 标定完成后的彩排与正式场。
**模式乙（人工就位 + 脚本击发）**：人手动把 App 打开到目标页、展开票档/规格、勾好观演人；脚本只做"本地倒计时 + 那一下点击 + 上报"。**这是 P0 的一等公民，不是丢人的兜底**——两轮彩排的第一轮建议就用它，把变量一个个隔离清楚，再切模式甲。

> 大白话：先让枪能响（模式乙，靶场），再练"整套动作自动完成"（模式甲，考场）。

## 5. 模拟器方案的可行性与取舍（重点三）

### 5.1 判定表

| 维度 | PC 安卓模拟器（雷电/夜神/MuMu/自建） | 安卓真机 | 云手机（别人的容器农场） |
| --- | --- | --- | --- |
| 风控检测面 | **高**：系统属性（`ro.kernel.qemu`、`ro.product.*` 的 generic/sdk 特征）、`/dev/qemu_pipe` 等设备节点、传感器恒定值、触控压力恒 1.0、指令转译时延等（OWASP MASTG 有公开检测项清单） | 低（但**不等于免疫**，见 5.2） | 高（你就是"模拟器"）+ 控制权不在你手里 |
| 性能/时延 | ARM 应用需转译（libndk/libhoudini），有损耗 | 原生 | 网络时延不可控 |
| 成本/运维 | 低（一台电脑开多台） | 中（设备+HUB+供电） | 按台付费 |
| 控制权/资产 | 在你手里 | 在你手里 | 账号登录在别人机器上 |
| 结论 | **只用于开发调试 / 流程彩排（不登真实高价值账号）** | **正式场次唯一选择** | 不用于正式场次 |

**为什么"正式场次必须真机"不是迷信**：检测一旦命中，代价是账号级、不可逆的（滑块死循环 / 黑号 / 取消资格），而抢购的价值偏偏集中在防守最严的平台上。"单台真机调通"的价值大于"十台模拟器全部被拉黑"，这句话在工程上是对的。

### 5.2 真机 ≠ 免疫：别忘了另一半"自动化检测"

审查抓出的重要补充：风控查两类东西——**① 模拟器检测**（真机解决）；**② 自动化检测**（真机也不能免疫）：无障碍服务列表里挂着 AutoX（部分应用会查）、注入点击无真人抖动、同 IP/同设备多账号关联。对策（行为纪律，写进运行手册）：

- 单账号单设备；监控轮询用低频 + 退避（**10~30 秒级，绝不用社区那种 0.2 秒高频轮询**）；
- 不 root；Shizuku 只用于"无障碍服务自愈"和必要时的 shell 兜底；
- 非窗口期不高频操作；窗口期也不"连发"（提交只发一下，沿用现有"只发一发、绝不重试"纪律）；
- 可选增值动作：找一台旧真机当**检测靶机**，先用公开检测脚本（OWASP MASTG 思路）摸清各平台实际在意哪些项，再定细节。

### 5.3 结论与用途分档

| 用途 | 用什么 | 备注 |
| --- | --- | --- |
| 脚本开发 / 元素侦察 / 流程彩排 | Windows 本机：Android Studio 自带模拟器（AVD）或 docker-android | **不登真实高价值账号**；跑的是"流程能不能通" |
| 将来有 Linux 机器时的高密度彩排 | redroid（Docker 跑安卓，ARM 应用靠 libndk 转译） | 需要 Linux 内核模块（binderfs 等），Windows 本机不实用，**不必现在折腾** |
| 正式抢购 | **安卓真机**（当前 1 台） | 标定 8 项通过后上岗 |
| 多机扩容（P2） | USB HUB + 多台真机；管理工具评估 QtScrcpy 群控 / STF | 见 §6 |

## 7. 与现有系统的整合（落地设计）

### 7.1 改动清单

**桥接服务新增接口（拟定，全部沿用现有 `/api/` 风格，仅本机）**：

| 接口 | 用途 |
| --- | --- |
| `GET /api/device/list` | 设备清单 + 状态（心跳、模式、绑定、最近结果） |
| `POST /api/device/setup` `{serial}` | **一键拉起**（§4 十步），返回分步结果 |
| `POST /api/device/stop` `{serial}` | 停 Agent / 撤任务 |
| `GET /api/device/task?deviceId=` | Agent 长轮询取任务（无任务挂起 ≤25s） |
| `POST /api/device/heartbeat` | 心跳（5s） |
| `POST /api/device/report` | 事件/结果上报 → 内部去重后转发到现有结果管线 |
| `POST /api/results/:platform` | **保持原样**（Agent 直报也可走这里；只加去重） |

**控制台**：新增 `web/tools/tool-devices.html`（设备页：卡片式，每台显示在线状态、当前任务、最近结果，操作按钮：拉起 / 就位 / 派发 / 停止 / 投屏 / 报警灯）；在 `web/workbench.html` 登记入口。

**配置**：新增 `data/grab/devices.json`（设备 ↔ 平台 ↔ 目标 ↔ 模式）；目标引用 `<平台>.config.json` 的 `products[]`（**白名单只有一个源，不复制**）。

**沿用现有纪律**：adb 子进程 spawn 一律 `windowsHide: true`（防黑窗，本机已有教训）；配置写入走 deepMerge 局部合并；控制台改完配置即时刷新下拉/设备列表。

### 7.2 白名单与安全（硬闸门位置）

- **闸门 1（派发时）**：桥接生成任务单时，目标必须是 `<平台>.config.json` 里 `enabled` 的商品且规格在勾选范围内——**复用现有槽位闸门的同款哲学**（精确匹配、命不中即拒绝、不兜底）。
- **闸门 2（任务单内冻结）**：任务单携带白名单**快照指纹**（hash）。手机即使断网也能用本地快照自校验；桥接派发时用同一算法对比当前配置，不一致 → 拒绝派发（等人确认）。
- **闸门 3（端侧执行前）**：Agent 校验 `taskId` 在白名单快照内、未过期、未击发过——三条全过才允许行动。
- **安全边界**：桥接继续只监听 `127.0.0.1`；`adb reverse` 天然把访问限制在"这两台设备之间"。**将来若要开局域网多机模式**，必须先做三件事：设备令牌、IP 白名单、收掉现有 `Access-Control-Allow-Origin: *` 通配（现为历史遗留，属 P2 硬化项）。

### 7.3 人工接管（滑块的答案）

- QtScrcpy 窗口常开（`--serial <序列号>`，多机时用群控界面）；
- Agent 一检测到滑块/风控层特征 → 上报 `risk_challenge` → 控制台蜂鸣 + 红字 + 自动把对应投屏窗置顶；
- 人 1 秒内滑完，App 继续流程；脚本不抢着"自动过滑块"（自研破解滑块 = 高维护成本 + 高风控暴露，否决）。
- 残余风险：无人看守时段遇到滑块 = 该场失败——**接受此边界**（用户选择场次时自然会守着）。

## 9. 风险与合规边界（必读）

1. **平台条款**：自动化工具可能违反平台用户协议，风险与账号绑定，本方案的价值是"把可控的都控住"，不是"保证不被发现"。建议专用账号、与日常账号隔离。
2. **实名制与倒卖红线**：大麦等实名票务，一证一票、不得囤票倒卖；本系统定位是"帮自己买到"，不是黄牛工具。
3. **账号安全**：测试全程**不提交支付**（止步支付页）；关闭免密/自动扣款；演练用冷门目标。
4. **数据安全**：观演人姓名/身份证等个人信息落在 `data/` 配置里——**确认 `.gitignore` 覆盖 `data/grab/`，绝不进仓库**；日志不打印证件号。
5. **频率纪律**：非窗口期低频 + 退避；窗口期"只发一发、绝不重试"；绝不学社区脚本的"5 进程并发提交"（风控特征明显）。
6. **工程风险**：端侧引擎是社区开源项目（AutoX.js 为个人维护），要把 APK 固定版本留存、脚本只用稳定子集（选择器/HTTP/文件/线程），防"引擎换代伤筋动骨"。

## 10.1 审前复杂度评估（Scope Challenge）

初稿想一步到位：全自动拉起 + 实时消息总线（WebSocket）都塞进 P0。按"每增加一个活动件就多一个坏点"的原则：

- 收窄 1：**P0 拆两段**——P0a 监控先行（只读、低风险、可长期跑），P0b 击发（标定合格才开）。★ 已采纳
- 收窄 2：**砍掉 P0 的 WebSocket 与 3210 端口**，用 HTTP 长轮询（§3.1）。★ 已采纳
- 结果：起步阶段的活动件从"桥接 WS + 设备页 + Agent + 拉起全链"降为"桥接设备 API（5 个接口）+ 设备页 + 薄 Agent"。**审查口径：scope reduced per recommendation。**
