## 0. 结论速览

**覆盖判断成立。** v3 第一梯队里，大麦（演唱会票）、T-FAMILY、POP MART、米哈游/叠纸/宝可梦周边、PS 限定，全部落在淘宝/京东/大麦三家 APP 上。华为项目打通的 Web/CDP 经验（对时、脱管定时器、体检探针、白名单铁律、验证码转人工）可以复用**方法论**，但通道本身不能复用——APP 没有 CDP，必须另建一条「控制台 ↔ 手机」链路。

**三大难点的答案，一句话版：**

| 难点 | 答案 |
|---|---|
| 通讯与调度 | 指令面与执行面分离：PC 端 Node `device-hub` 独立进程负责编排/对时/监控；**毫秒级开火不依赖网络信号到达时刻，靠「三层对时 + 到点本地触发」**。通道用 adb 本地回环（forward/reverse），不出局域网 |
| 一键拉起 | 三级路径：`am start` 冷启兜底 → deep link 直达详情页 → APP 内「预航」到提交前一跳。开售前 3-5 分钟完成预航，到点只补最关键的 1-3 次点击 |
| 模拟器 | **开发调试可用，实弹禁用。** 登录、实名、下单支付三个环节绝不上模拟器；实战一律真机集群（二手千元机即可）。低频只读监控（回流票盯梢）可以用模拟器/云手机跑 |

**热路径主路线（经审查修正后）：**

- **Route A（先落地）**：PC 驱动 [uiautomator2](https://github.com/openatx/uiautomator2)（8.4k★，MIT，2026-10 仍在活跃提交），每击 10-80ms，社区已验证的大麦 App 端路线。
- **Route B（毫秒级进阶）**：自研无障碍 APK 常驻手机端 + 本地时钟开火（借鉴 DaMaiHelper / Hamibot 架构），把热路径压到零网络往返。
- **监控墙**：scrcpy（151.7k★，v5.0.1 活跃）多机画面矩阵 + 应急人工接管。

**明确不做**：协议直刷 / 抓包重放（mtop x-sign 依赖阿里无线保镖闭源 SDK、频繁变更、有判例风险，且违反本仓库「不构造、不重放请求」铁律）。详见 §7。

> ⚠️ 最初草案把 AutoX.js 当作手机端运行时核心，审查时核实 **kkevsekk1/AutoX 已删库（404）、原版 Auto.js 2021 年删库**，已降级为思路来源。这正是「先检索核实再定方案」的价值。

## 2. 总体架构

```
                      Windows 控制台 (PC, Node.js)
┌─────────────────────────────────────────────────────────────┐
│  web/workbench.html 门户                                     │
│    └─ 设备面板(新增)：设备列表/布防状态/心跳/告警/一键拉起        │
│                                                              │
│  core/grab-bridge.mjs  :3100（现有，不改动其职责）              │
│  core/device-hub.mjs   :3120（新增，独立进程，§3.2）           │
│    ├─ 设备注册 / 心跳(5s) / 掉线告警                           │
│    ├─ 对时服务（NTP 采样 + 平台 HTTP Date 交叉校准）             │
│    ├─ 场次编排（T-60 布防 → T-30 体检 → T-5 拉起 → T-0 开火）    │
│    └─ 派发器：adbkit(Node) / u2 驻留进程(HTTP) / adb CLI        │
└───────────┬─────────────────────────────────────────────────┘
            │  USB adb（主通道）；Android 11+ 无线调试（备份）
            │  adb forward tcp:7912 → 手机 u2 服务   (Route A 指令)
            │  adb reverse tcp:3120 ← 手机 Agent     (Route B 指令/回报)
┌───────────▼─────────────────────────────────────────────────┐
│  Android 真机 ×N（每机 = 1 个账号槽位，同槽位语义）              │
│    淘宝 / 京东 / 大麦 APP（提前登录 + 实名 + 收货/观演人配置）    │
│    Route A：uiautomator2 device 服务（被动接令，PC 驱动）       │
│    Route B：自研无障碍 APK（常驻，本地钟到点开火）                │
│    scrcpy-server（画面回传监控墙，随时可人工接管）                │
└──────────────────────────────────────────────────────────────┘
```

**职责边界（关键设计决策：执行体尽量靠近手机，决策体留在 PC）：**

| 环节 | 谁负责 | 为什么 |
|---|---|---|
| 决策（抢什么、几点、白名单） | PC 控制台 | 人机交互、配置、复盘都在这 |
| 对时 | PC（NTP+平台校准），必要时下发给手机 | PC 资源足、算法好做 |
| 场次编排（时间轴） | PC device-hub | 槽位/设备状态全局可见 |
| 拉起/预航 | PC 发令，手机执行 | 大延迟动作（秒级），不在乎指令往返 |
| **开火（到点关键点击）** | **Route A：PC 按对时结果驱动；Route B：手机本地钟** | 消除网络抖动，见 §3.3 |
| 结果回报/日志 | 手机 → PC（adb reverse） | 复盘与告警 |

## 3. 难点一：控制台与手机端的通讯与调度机制

### 3.1 通道选型对比（全部基于 2026-10 核实的开源生态）

| 通道 | 方向 | 延迟量级 | 依赖 | 结论 |
|---|---|---|---|---|
| adb forward + u2 JSON-RPC（HTTP） | PC→手机 | 每击 10-80ms | uiautomator2 自带端口转发 | **Route A 主通道** |
| adb reverse + WebSocket | 手机→PC（也可反向） | 单消息 5-30ms | 标准 adb 能力 | Route B 指令/回报通道、心跳日志 |
| adb shell input tap | PC→手机 | 数百 ms/击（每次 fork app_process） | 无 | 只用于非关键路径 |
| scrcpy 注入（InputManager.injectInputEvent） | PC→手机 | ~10ms/击 | scrcpy-server；编程化注入需实现其控制协议 | 监控+人工接管；Route B 备选 |
| HTTP 轮询 | 双向 | 秒级，且风控差 | — | 否决 |
| 商业云（Hamibot REST 下发） | 云→手机 | 不确定 | 数据出第三方、账号绑其云 | **只借鉴架构，不引入运行时** |

### 3.2 device-hub 设计（独立进程）

**为什么独立进程**：桥接铁律是「改 `core/` 后重启服务」。如果 device-hub 长在 `grab-bridge.mjs`（现 1538 行单文件）里，每次改桥接代码重启服务，都会解除已布防手机的布防状态——抢购前夜这是不可接受的爆炸半径。[P2 见附录A F4]

```
core/device-hub.mjs        # 新增，:3120，仅 127.0.0.1
  ├─ POST /api/devices/register      # 手机 Agent 上线注册（serial/型号/电量/APP 版本）
  ├─ GET  /api/devices               # 设备列表+状态（workbench 轮询或代理）
  ├─ POST /api/devices/:id/arm       # 布防：下发场次任务（白名单、t_fire、动作序列）
  ├─ POST /api/devices/:id/fire      # Route A 手动/自动开火（预航已完成时）
  ├─ POST /api/devices/:id/report    # 状态回报（阶段推进/结果/异常）
  └─ WS   /agent                     # Route B 手机 Agent 长连接（经 adb reverse）
data/grab/devices.json     # 设备槽位表：serial/别名/绑定账号/平台/状态（沿用槽位语义）
platforms/app/             # 新增平台目录：app-pilot（u2 驱动）/ deeplink 库 / 预航脚本
```

Route A 的驻留设计：T-5 分钟时为每台设备拉起一个 Python u2 驱动进程（`platforms/app/app-pilot`），进程常驻并在本地监听；T-0 的开火只是一次 `127.0.0.1` HTTP 调用（5-20ms），避免临时 spawn 进程的 100-300ms 开销。

### 3.3 三层对时与到点开火（成败关键）

抢购的毫秒级优化，全部建立在对时准确之上。三层缺一不可：

1. **PC ↔ NTP**：进程内直连 NTP（阿里云 ntp / pool.cn），采样 20 次取**最小 RTT 样本**的 offset（RFC 5905 标准算法）。不要依赖 Windows w32time（默认精度 10-100ms 且被域策略干扰）。
2. **PC ↔ 平台服务器**：拉取详情/订单接口的 `Date` 响应头（秒级精度）做交叉校准；真实开售时刻以**当期场次实测**为准，每场复盘修正（沿用华为「10:16 复盘」方法）。
3. **PC ↔ 手机**：经 adb 通道 echo 往返采样 10 次取 min-RTT，得手机钟 offset（仅 Route B 需要）。

**开火策略**：`t_fire = T_open + offset + lead`。`lead`（提前量）由演练标定，默认 0、可负值；Route A 由 PC 在 `t_fire` 触发本地 HTTP 调用，Route B 将 `t_fire` 下发、手机用自身单调钟到点触发——**开火瞬间没有任何网络等待**。

**多机抖动**：多台设备同一毫秒做同一动作是行为聚集信号。抖动窗口 ±0~80ms 可配置，默认小抖动；代价是可能慢几十毫秒，由场次类型决定（大麦实名票建议开，普通上新可关）。[P2，F6]

### 3.4 场次调度时间轴

```
T-60min  布防检查：设备在线/电量/存储/APP 版本/登录态
T-30min  探针体检（沿用华为体检思路）：u2 空跑一遍预航路径，到提交前一跳即停，不提交
T-10min  三查：登录态、网络、前台服务；异常→告警转人工
T-5min   拉起 + 预航：deeplink 直达详情页 → 推进到提交前一跳；Route A 拉起 u2 驱动进程
T-1min   静止待命（不再有操作，让页面状态稳定、也降低风控敏感度）
T-0      开火：刷新 → 关键点击 1-3 次（立即购买 → 提交订单）
T+10s    结果回报：成功→记录；失败（验证码/缺货/页面改版）→ scrcpy 人工接管 + 告警
T+30min  自动复盘：时间轴全程记录（沿用 data/grab 证据落盘惯例）
```

## 4. 难点二：一键拉起的实现路径

### 4.1 三级拉起

```bash
# L1 冷启动兜底（最慢 1.5-3s，仅当 APP 未运行）
adb -s <serial> shell monkey -p cn.damai -c android.intent.category.LAUNCHER 1

# L2 deep link 直达（热启动 300-1500ms）
adb -s <serial> shell am start -a android.intent.action.VIEW -d "taobao://item.taobao.com/item.htm?id=6798xxxxxx"

# L3 APP 内预航（u2/无障碍序列）：详情页 → 点「立即购买/选票档」→ 停在「确认订单/提交订单」前一跳
```

### 4.2 deep link 现状核实表（2026-10-08）

| 平台 | 包名 | scheme（社区验证格式） | 核实状态 |
|---|---|---|---|
| 淘宝 | `com.taobao.taobao` | `taobao://item.taobao.com/item.htm?id=<商品ID>`；天猫 `taobao://detail.tmall.com/item.htm?id=` | 社区多源一致（CSDN/cnblogs）；**上线前需在当期版本真机回归** |
| 京东 | `com.jingdong.app.mall` | `openapp.jdmobile://virtual?params={"category":"jump","des":"productDetail","skuId":"<SKU>"}`（params 整体 URL 编码） | 社区多源一致，官方未公开文档；同上需回归 |
| 大麦 | `cn.damai`（已核实） | `damai://` 具体路由**未能核实** | **阶段0 探针任务（F2）**：`apkanalyzer`/`aapt2 dump badging` 反解 APK 的 AndroidManifest 抓 scheme，配合 `adb logcat` 人工导航时抓路由；在核实前**任何依赖大麦 deeplink 的预案不得上线** |

兜底：deeplink 失败自动降级 L1 + u2 搜索/点击导航（慢但可靠）。

### 4.3 保活与预热

- 电池白名单 + 关闭省电限制；Route B APK 用前台服务常驻。
- 关闭系统「应用商店自动更新」+ APP 内更新弹窗预案（弹窗是预航脚本的头号杀手，预航序列要含弹窗检测关闭分支）。
- 登录态保鲜：T-30 体检含登录探测（语义沿用 `tools/check-slot-logins.mjs`），掉线立即告警人工处理——**绝不自动重登录**（滑块+短信验证码）。
- 每台机一个账号、一个平台角色（大麦需提前配好观演人实名信息；淘宝/京东配好默认收货地址与支付方式）。

### 4.4 批量拉起（示意；正式实现走 adbkit 并发 + 结果回报）

```bash
for s in $(adb devices | awk 'NR>1 && $2=="device"{print $1}'); do
  adb -s "$s" shell am start -a android.intent.action.VIEW -d "<deeplink>" && \
  echo "$(date +%T) $s launched"
done
```

## 5. 难点三：模拟器方案的可行性与取舍

### 5.1 主流模拟器现状（2026-10）

| 模拟器 | ADB | 多开 | 自动化兼容 | 一句话结论 |
|---|---|---|---|---|
| MuMu | 7555 起，完善 | 强（安卓 12/15 双 ROM） | uiautomator2 生态兼容最好 | 开发调试首选 |
| 雷电 LDPlayer | 5555 起 | 成熟，`ldconsole` 命令行批量启停 | 可用，有已知小坑 | 脚本化多开首选 |
| 逍遥 MEmu | 支持 | 极限多开、CPU 控制好 | 可用 | 资源占用优 |
| 夜神 Nox | 支持 | 支持但内核老（安卓 7/9） | 可用 | 不推荐，更新慢 |
| Google AVD | 原生 | 多实例 | 原生兼容 | `ro.kernel.qemu=1` 等特征极易被识别 |
| Genymotion | 支持 | 多实例 | 支持 | 商用许可；QEMU 系特征明显 |
| Waydroid | 支持 | 容器级 | 需 ARM 转译 | 跑国产 APP 无成熟案例 |

### 5.2 风控检测维度（为什么实弹不能上模拟器）

| 检测维度 | 内容 | 对我们的影响 |
|---|---|---|
| 系统属性 | `ro.kernel.qemu`、`ro.build.fingerprint`、build props 异常 | 阿里系（淘宝/大麦共用 MTOP + 无线保镖风控）重点检测 |
| 硬件缺失 | 传感器（加速度计/陀螺仪）、电话模块、基站信息 | 模拟器普遍缺失或伪造痕迹 |
| 注入特征 | MotionEvent 来源（无障碍/u2 注入 vs 真人触摸） | 易盾已公开研究；**真机+无障碍同样有此特征**，需行为拟人化 |
| 环境聚集 | IP 聚集、多开同质化、行为同步 | 多开模拟器三信号齐中 |

佐证：安全客/看雪的模拟器检测技术资料、网易易盾《Android 模拟点击研究》；[currycan/HaTickets](https://github.com/currycan/HaTickets) README 明确警告"自动化可能触发限流甚至封号，模拟器比真机更容易触发"并要求 Android 12-14 真机；极验博客称"PC 模拟器+代理多开场景封号率超 60%"（**厂商口径，仅作方向参考**，见附录B）。大麦强实名，封号代价远高于普通账号。

### 5.3 使用边界（三档）

| 档位 | 场景 | 环境 |
|---|---|---|
| ✅ 可以用 | 脚本开发调试、控件定位、dry-run 演练、**回流票低频只读监控**、多账号管理后台 | MuMu/雷电 + 小号 + 固定环境 |
| ⚠️ 谨慎用 | 淘宝/京东的浏览、加购等非关键路径（测试账号） | 小号，接受损失 |
| 🚫 禁止 | **登录绑定新设备、实名信息填写、下单支付**（尤其大麦实名主流程）；任何协议直刷 | 只用真机 |

### 5.4 真机集群：成本与运维

- 二手安卓机 100-300 元/台（骁龙 660 级即可，抢购对性能要求极低、对「不被识别」要求极高）；建议 Android 11-14。
- USB Hub 带独立供电（60W+），一台 PC 挂 4-8 台；Android 11+ 无线调试（`adb pair`）作备份通道（延迟抖动大，只做监控不做开火）。
- 设备槽位表（`data/grab/devices.json`）沿用现有账号槽位语义：serial ↔ 账号 ↔ 平台 ↔ 状态。

## 7. 协议直刷 / 抓包重放：为什么不走（记录在案的否决理由）

1. **技术**：App 端签名 x-sign / x-mini-wua / x-sgext 依赖阿里无线保镖闭源 SDK，随版本频繁变更，公开项目（如 taobao-x-sign）基本失效；活跃的 [cv-cat/TaoBaoApis](https://github.com/cv-cat/TaoBaoApis)（334★）也只覆盖私信/客服接口、不下单。H5 端 `MD5(_m_h5_tk&…)` 虽公开，但下单接口需完整 cookie/cna/umid 且频控+滑块极严。
2. **风控**：协议直刷绕过 APP 行为层，特征最干净也最显眼，风控等级最高（京东 eid/fp 系路线 2021 后公开层面全灭）。
3. **法律与铁律**：存在破坏计算机信息系统、不正当竞争判例；且直接违反本仓库「不构造、不重放请求」铁律。UI 自动化让 APP 自己走完下单流程，是唯一与现有铁律一致的路线。

## 9. 风险清单与兜底

| 风险 | 信号 | 兜底 | 验证方法 |
|---|---|---|---|
| 风控（设备指纹/行为） | 验证码变多、限流 | 行为拟人化（贝塞尔轨迹、变速滑动）、可配置抖动、小号先行；**无任何方案承诺存活率** | 小号灰度场次观察 |
| 无障碍/u2 服务被杀 | 心跳丢失、体检失败 | 前台服务+电池白名单；T-10 三查兜底 | 阶段1 演练含强制杀进程用例 |
| USB/adb 断连 | 心跳掉线 | 自动 `adb reconnect` + 声光告警；无线调试备份通道（仅监控） | 演练中拔线用例 |
| APP 版本更新/弹窗致控件路径失效 | T-30 体检失败 | 预航序列含弹窗分支；体检不过→禁止布防并告警 | 版本升级后强制体检 |
| 验证码（滑块/点选） | 开火遇验证码 | **转人工**：手机响铃+控制台告警，scrcpy 手动接管，Agent 暂停等待 | 演练人工接管计时（目标 <15s 接管） |
| PC 时钟漂移 | offset 分布异常 | 每场 T-60 重新采样；异常值剔除（min-RTT 法天然抗钟漂突变） | 对时脚本输出分布报告 |

失败模式检查：以上均无「无测试 + 无错误处理 + 静默失败」路径；心跳与体检保证失败必然**可感知**。
