## 二、P0 崩溃（已修复）：preOpenedConfirm 的 TDZ

**现象**：任何"定时场次 + 提前 65 秒以上派发"的标准跑法（值守到 T0），走到"就位"阶段就抛：

```
ReferenceError: Cannot access 'preOpenedConfirm' before initialization
```

槽位在 `Promise.allSettled` 里记成"异常"，整个槽位报废（不会抢、不会自动回落）。

**根因**：19:50 那次修复把"预开确认页"整块从 `sleepUntil` 之后上移到"就位"之后（修 placement），但 `let preOpenedConfirm` 的声明还留在原处（热循环区、下方）。JS 的 `let` 有 TDZ：执行到预开块（条件：距 T0 > 65s，正是常规场景）时声明尚未执行 → 直接抛错。

**证据**（三重）：
- tsc 静态检查报 4 处 `TS2448: Block-scoped variable 'preOpenedConfirm' used before its declaration`（原 651/654/659/661 行）；
- Node 最小复现：同结构 → `ReferenceError: Cannot access 'preOpenedConfirm' before initialization`；
- 旁证：19:50 记忆里该项修复标注"待验证：下次定时测试看日志"——未曾复跑，所以没被抓到。

**修复**：把 `let preOpenedConfirm = false;` 上移到首次使用之前（新 576 行，`if (triggerLocalMs && ...)` 之上，仍在函数顶层保证热循环可见）。**零行为变化**，只消除崩溃。

**复验（全部通过）**：
- `node --check platforms/huawei/cdp-rush.mjs` → 语法 OK；
- tsc 复扫 → TS2448/TS2454 **清零**；
- grep 核对：全部 11 处引用都在声明之后。
- 桥接每次派发重新 spawn 驱动（grab-bridge.mjs:68），**无需重启服务，下次派发生效**。

## 三、降级逻辑逐项核对（对照"内部失败→立即降级"的要求）

### 3.1 购买侧：不是串行降级，是"并行冗余"——效果更稳，但有两处名不副实

- 内部 fire 与点击路径**同时在工作**：热循环里 `internalFire()`（每 ≥300ms 一次，1195 行）与 `fc.buy` 检测→`clickBuyFlow`（1232 行）互不依赖。也就是说，即使内部入口全废，只要按钮可见，点击照常出手——**"立即降级"的效果由并行实现**，这一点是达标的。
- 问题 A：**"停用判定"比文档慢 6 倍**。`internalMissStreak >= 200`（810/842 行）按 fire 节拍 300ms 算 ≈ **60s**，注释写"≈10s"——那是按 50ms/轮 的旧节拍推的，但 fire 被 `Math.max(300, hotMs)` 节流。影响：结构失效后 60s 内每轮仍浪费一次探测（~5ms），且日志"持续不可达"误导。**建议**：改成时间判定（如 `missSince` 起算 10s）或把阈值改为 33。
- 问题 B：**"调到了但没效果"不计失败**。missStreak 只统计"不可达/异常"；`Yo` 若还在但语义变了（改版后静默无效），内部侧永远显示"成功"。实际风险被并行点击兜住，但日志会骗人。**建议**：可选加"连续 N 次调用后仍 30s 无确认页 → 记一次降级事件"，仅加日志不加动作。

### 3.2 提交侧：真串行降级，但降级**不快**、失败**不回头**

- 现状链路（1346-1413 行）：内部 `handleOrderSubmit` 优先；`NO_BUTTON` → 每 300ms 等挂载（最多 40 轮≈12s，属"页面加载"可辩护）；`NO_ENTRY/ERR` → **先重试 6 轮 ≈1.8s 才降级**；降级后 = 滚动 + **固定 `sleep(300)`** + 重取坐标 + 点击（实测点击 47ms）→ **合计实测 ~352ms，超 0.1s**。
- **FIRED 后不验证、失败不重试**：内部提交一旦调用成功即跳过点击、12s 轮询结果，拿不到订单号就报 RESULT_UNKNOWN 收尾——防重复下单的考虑成立，但结合 3.3 的提前量问题，风险被放大。

### 3.3 预开路径的时序问题（P1，需实战确认）

- `T0_ACT_LEAD_MS = max(500, leadMs+200) = 500ms`（1126 行）是给**点击路径**设计的安全提前量（按钮锁定期间做无效动作无副作用）。
- 但预开分支（1176 行）用的就是 `canAct`（T0-500ms）→ **预开的确认页在 ≈T0-500ms 就真提交了**，早于 R1 解锁点（T0-300ms）也早于真 T0。而设计意图（记忆/注释）是"**T0 只提交**"。
- 若服务器拒收 T0 前的提交 → 出现"提交被拒但无重试"的最坏情况（整槽 RESULT_UNKNOWN 收尾）。
- **处置建议**：下一次定时演练时（现货挂 saleAt）盯日志"到点：在预开的确认订单页上直接提交"，看服务器是接受（出订单号/收银台）还是拒绝（提示"未开始"等）。若拒绝，把预开分支的触发改成独立闸门：`Date.now() >= triggerLocalMs - (leadMs||300)`（解锁点）或 ≥ `triggerLocalMs`。

### 3.4 竞态结论：**未发现会重复下单的竞态**

- 核对确认：提交链路同一时刻只有一条在跑（`maybePickConfirm` 与 `attemptBuy` 都在主循环里 await，不会并发）；预开的确认页被正确排除在 `maybePickConfirm` 之外（在 `tabBaseline` 里，876-881 行）。
- 偶发冗余：内部 fire 与点击可能各开一个确认页草稿 → `finishConfirmed` 里有去重关闭（保留 1 个，其余 close）；草稿页不提交，**无害**。内部 fire 不 await，槽位收尾后可能有"在飞的"一次调用再开个草稿页——同样无害。
- 唯一值得处理的健壮性问题：`attemptBuy`（888 行）里 `const tabs = await listTabs(port)` 无 catch，Chrome 瞬断会抛异常终止整槽（外层只记异常，不会自愈）。**建议**：`.catch(() => [])`。

## 四、耗时实测（对照"除页面加载外全部 ≤0.1s"）

基准环境：真实 Chrome 154 headless + 与生产一字不差的三段表达式 + 生产同款 CDP 调用链（假 fiber，闭包/Scopes 真实）。真实页面 payload 更大、栈更深，耗时会略增，但同量级。

| 操作 | p50 | p90 | max | 判定 |
|------|-----|-----|-----|------|
| 内部购买链（全链：legacy 探测+7 跳闭包扫描+调用） | **4.6ms** | 8.6ms | 12.6ms | ✅ 达标（README 称"~5ms"，属实） |
| 内部提交链（单次 evaluate → FIRED） | **0.5ms** | 0.7ms | 4.0ms | ✅ 达标 |
| trustedClick 兜底点击（3 个真实输入事件） | **47ms** | 62ms | 62ms | ✅ 达标（其中 30ms 是固定 sleep，cdp-core.mjs:210） |
| listTabs（/json/list 拉取） | 1.0ms | 1.7ms | 1.7ms | ✅ |
| **提交兜底完整链（滚动+300ms 硬睡+重取坐标+点击）** | **357ms** | 362ms | 362ms | ❌ 超标 3.6 倍 |
| 检测节拍：热循环（50ms 睡 + fastCheck） | ~51-65ms/轮 | — | — | ⚠️ 解锁→点击合计 ~110ms，压线/略超 |

**节拍层面补充**（含等待，非单次操作）：
- 点击路径：解锁 → 发现（≤1 轮 ≈65ms）→ 点击（47ms）≈ **~110ms**；
- 内部路径：fire 被 300ms 节流，解锁瞬间若在两拍之间，最坏多等约一拍（**0~350ms**，平均 ~170ms）；
- 提交侧：NO_ENTRY 降级前多等 1.8s；点击后无确认页要等满 30s 才重试；内部失效停用要 60s。

## 五、待拍板 / 建议改动清单（按优先级）

1. **演练确认**：预开路径 T0-500ms 提交是否被服务器接受（见 3.3）。拒绝则改预开分支闸门。
2. **提交兜底提速**（要 0.1s 达标必须动）：`sleep(300)`（1404 行）→ 缩到 ~80-120ms 或改"等到坐标稳定"（两次测量一致）；`NO_ENTRY/ERR` 的 6 轮重试（1357 行）→ 直接降级或只留 1-2 轮。
3. **attemptBuy 窗口**（888 行）：抢购热段 30s → 3~5s；30s 留给回流监控段。
4. **内部失效判定**（810/842 行）：200 次 → 按时间 10s（或阈值 33）。
5. **兜底质量**：`attemptBuy` 的 listTabs 加 `.catch(()=>[])`；可选给 `trustedClick` 的 30ms 睡眠降到 20ms（press/release 间隔）。
